# Updating Lutra

Open **About**, check for updates and choose **Install update**. A preview installation includes preview releases by default; the checkbox allows stable releases only. Stable installations default to stable releases. Versions follow semantic precedence, so `preview.10` is newer than `preview.2`, and a stable release supersedes its previews. The updater never selects an older version.

Downloads come only from [Resnais-Beefhair/lutra releases](https://github.com/Resnais-Beefhair/lutra/releases). The Windows x64 package must be named `Lutra-<version>-win-x64.zip`. It may contain one enclosing directory or place the application files directly at the ZIP root. The installed application and service version must match the release tag. Source-code archives are not installable packages.

## What happens during an update

1. Checking and downloading do not stop cooling control. Lutra compares up to the most recent 1,000 published release records, excludes drafts and the unselected preview channel, and chooses the highest eligible version.
2. The download is checked against its exact GitHub size and SHA-256 digest. Releases without a valid GitHub asset digest are ineligible for automatic updating. A truncated, modified or oversized download is rejected.
3. Windows requests administrator approval. Cancelling leaves the current installation and service untouched. Updating requires the installed Program Files copy; a portable or developer build cannot replace the service through this button.
4. The **existing installed** updater re-fetches the exact release from GitHub, copies the ZIP into an administrator-protected staging directory, and verifies the protected copy again. It rejects ZIP traversal, links, case-insensitive duplicate paths, Windows device names, more than 5,000 entries, entries above 256 MiB and total expanded contents above 1 GiB. It never executes a downloaded install script.
5. A fresh, running controller with no active errors or alarms is required. All enabled temperature sources and outputs must be available; QUADRO pumps need a fresh nonzero tachometer reading. Preparation, durable configuration backups and file copying finish before the service is stopped. The updater then registers a protected SYSTEM recovery task, records the original binary hashes and arms a durable transaction journal.
6. The monitor exits. The installer stops the service, retains the previous installation beside the new one, and replaces the application files. Configuration, calibration, device settings, owner identity and history are not reset. The service reloads the saved configuration normally.
7. Five consecutive fresh healthy states are required after restarting. If activation fails, the updater attempts to restore the previous binaries and saved configuration/owner file, restart the previous service and check it again. If the updater is terminated or Windows restarts mid-update, the recovery task retries every minute and at Windows startup. It takes the same exclusive transaction lock, verifies the saved files before stopping any remaining controller, and resumes restoration. Confirmed success or verified rollback removes the task. Results and backups remain available for diagnosis. The monitor reopens using its original user's token.

## Cooling during the handover

QUADRO native curves continue on the controller. Host-fed curves use their already commissioned device fallback when the software-sensor watchdog expires (approximately 15 seconds). Motherboard outputs return to firmware defaults when the service stops. The updater does not invent new fallback values or install drivers; safe fallback behavior must already have been verified for the hardware in use.

An update is not a substitute for commissioning. A device unplugging during replacement, a firmware problem, power loss or an operating-system failure can prevent verification or rollback. The health check confirms fresh inputs, reachable outputs and a running pump tachometer; it does not load-test the cooling loop or guarantee physical flow. If automatic restore reports a failure, use the retained previous installation and check cooling before continuing normal use.

Replacement uses two directory renames. A power loss or forcibly terminated updater between them can temporarily leave `%ProgramFiles%\Lutra` absent while previous binaries remain in `Lutra.rollback-<job>`. The protected recovery task restores that installation automatically once Windows and Task Scheduler can run. It also handles an interrupted restoration and leaves a committed, verified new version in place. Hardware fallback covers the waiting period; uninterrupted host control through power loss is not guaranteed. If the recovery result reports a persistent failure, an administrator can rerun the protected job's `Recover.ps1 -JobId <job>` using Windows PowerShell after checking the reported cause. The recovery script verifies saved binary and configuration hashes before stopping an existing controller. Do not delete or rename its backup directories while recovery is pending.

Results are stored in `%ProgramData%\Lutra\updates\<job>\result.json`; `RecoveryPending` indicates a retry is still required. Configuration backups, the transaction journal and protected recovery scripts are in the same job directory. The temporary task is named `Lutra Update Recovery <job>`. Previous application files are retained in `%ProgramFiles%\Lutra.rollback-<job>`; failed new files may be kept in `Lutra.failed-<job>` directories. The updater never deletes these backups automatically. Only remove old backups after confirming the new installation works and recovery is no longer pending.

## Trust and release requirements

The release digest is provided by GitHub's official [release asset API](https://docs.github.com/en/rest/releases/assets). It protects integrity relative to the selected trusted repository and downloaded metadata; it is not an Authenticode publisher signature. A compromised GitHub publisher account can publish a malicious release. Lutra does not disable Windows security, bypass a blocked driver or add antivirus exclusions.

Publish the application and service together with the same full version, include `tools/Update-Lutra.ps1` and `tools/Recover-LutraUpdate.ps1`, and upload the named release ZIP. Updates preserve the saved configuration and currently fail safely if a version unexpectedly changes it. A future configuration-schema migration needs an explicitly tested migration and rollback path before becoming eligible for this updater.

The tag-driven Release workflow builds and tests new packages in GitHub Actions and creates a build-provenance attestation for the exact ZIP before publishing it. See [Contributing](../CONTRIBUTING.md#releasing) for tag validation, manual candidate builds and `gh attestation verify`. Older manually published releases do not acquire attestations retroactively. The in-app updater still verifies the GitHub asset digest; it does not currently enforce attestations.
